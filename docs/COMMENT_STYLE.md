# 注释约定

本文件说明本仓库源码注释的写法。注释写给后来的维护者看，用来交代「为什么」，不是用来复述代码，也不是私人对话记录。

## 先问要不要写

只在注释能补上代码读不出来的信息时才写，例如：

- 设计原因、取舍和历史背景
- 边界条件、兼容性、不可见的安全或协议约束
- 复杂接口、数据结构或调用约定（按该语言的惯用形式，如 JSDoc、Python docstring、Shell 用法说明）
- 明确的待办：写清完成或解除的条件，不要只写一个名字或一句口头禅

不要为了凑数量给每一行、每一个字段加注释。不要把调试日志、临时对话口气或已经过时且不再有信息量的句子堆在代码里。

## 功能块注释

对一段完整功能，可以使用下面四段式块注释（行注释或块注释均可，按语言习惯选择）：

```
[位置:文件·函数或区块] [名称] [原因或约束，一句话或一小段] [注释时间 YYYY-MM-DD]
```

- **位置**：方便检索，写文件与函数（或区块）名。
- **名称**：这段功能叫什么。
- **原因**：写为什么这样做、边界或不可见约束，不要写「按某某说的」。
- **时间**：写这次注释或这次决策的日期。

结构要保留；内容必须是通用的工程说明。不要在注释里写私人约定编号、作者专属口吻或把需求归到某一个人名下。有用的日期、批次和技术原因可以保留。

## 怎么写原因

- 用中性、可验证的表述。安全相关约束必须写清楚且不得写弱，例如：所有出口必须走已配置代理，未配置时失败关闭，禁止回退到直连；登录和鉴权要求写明检查点，而不是「以后再说」。
- 兼容性、协议限制、以及「看起来能简化但不能改」的行为，要把原因写出来。
- 注释里不要写入真实口令、密钥、个人数据或其他生产敏感字面量。需要举例时用占位符或说明「从环境变量读取」。
- 用户可见文案、模型提示词、测试夹具或会进入模型上下文的字符串，不要在注释里改写成与源码不一致的「理想版本」。若注释必须引用这些原文，保持与代码一致，另开专门的文案审阅，不要只改注释。

## 待办

`TODO`、`FIXME` 要带上可检查的条件或期限，例如「待配置项 X 就绪后再启用」。不要写成「等某人来定」或只署名而不写内容。

## 不要做的事

- 不要用全局替换去「清理」某个字或某个名字：字符串、模板、正则、URL、许可证和第三方署名都可能被误伤。
- 不要为了迁就注释去改运行逻辑、标识符、持久化字段或测试断言。
- 不要改第三方代码里的版权和归属说明。
- 不要删除仍然有效的安全或兼容性说明。过时且已无信息量的注释可以在审阅后删除。

## 语言习惯

- JavaScript：功能块用 `/* ... */` 或 `//`；公开函数需要时用简短 JSDoc，说明参数与返回值中的非显而易见约定。
- Python：模块、公开函数和复杂数据结构优先用 docstring；行内 `#` 只补充 why。
- HTML / CSS / Shell：分别使用 `<!-- -->`、`/* */`、`#`；只注释非显而易见的布局、选择器或脚本约束。
- 其他语言：沿用该语言常见的文档注释形式，原则相同。
